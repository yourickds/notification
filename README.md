# Notification Service

Микросервис для асинхронной отправки уведомлений через различные каналы (Telegram, Email и др.) на базе Laravel 11.

## 🚀 Быстрый старт

### Требования
- Docker & Docker Compose
- Make (опционально, но рекомендуется)

### Авто-установка (рекомендуется)
```bash
make create
```
Эта команда выполнит: копирование `.env`, сборку контейнеров, установку зависимостей, миграции и сидирование.

### Ручная установка
```bash
# 1. Настройка окружения
cp .env.example .env

# 2. Запуск инфраструктуры
make up

# 3. Установка зависимостей
make install

# 4. Миграции и данные
make migrate
make seed
```

### Доступ к сервисам
| Сервис | Адрес | Примечание |
|--------|-------|------------|
| **API** | `http://localhost:8000` | Основное приложение |
| **phpMyAdmin** | `http://localhost:8080` | Управление БД (user: `user`, pass: `password`) |

## 🏗 Архитектурные решения

### 1. Стратегия (Strategy Pattern) для каналов отправки
**Проблема:** Необходимость поддерживать разные каналы (Telegram, Email, SMS) и возможность добавлять новые без изменения ядра.

**Решение:**
```
┌─────────────────────────┐
│   SendNotificationJob   │
└────────┬────────────────┘
         │              Делегирует
         ▼
┌───────────────────┐
│ ChannelDispatcher │
└────────┬──────────┘
         │              Резолвит из config('notifications.channels')
         ▼
┌──────────────────┐
│ ChannelInterface │ ◄── TelegramChannel, EmailChannel...
└──────────────────┘
```
- **Почему так:** Полное соблюдение **OCP (Open/Closed Principle)**. Добавление нового канала требует только создания класса и одной строки в конфиге. Контроллеры и Джобы не меняются.

### 2. Передача модели `Notification` вместо массива
Все методы интерфейса принимают типизированную модель:
```php
interface ChannelInterface {
    public function send(Notification $notification): bool;
}
```
- **Почему так:**
    - ✅ Полная типизация и автокомплит в IDE.
    - ✅ Доступ к связям (`$notification->user->email`) без передачи лишних данных.
    - ✅ Единый источник правды: канал берет `$notification->channel` из модели, а не из аргументов метода.

### 3. Гарантированная доставка через Очереди (Queue)
**Проблема:** Отправка уведомлений — внешняя операция, подверженная сбоям сети и таймаутам.

**Решение:**
- `SendNotificationJob` реализует `ShouldQueue`.
- Настроены **ретраи**: `$tries = 3`, `$backoff = 60` (сек).
- Разделение ошибок:
    - `FatalChannelException` (4xx) → логирование, статус `error`, **без ретрая**.
    - `Throwable` (5xx/сеть) → выброс исключения → **автоматический ретрай** очередью.

### 4. Flat Structure + Docker-first
**Проблема:** Сложности с путями, переменными окружения и зависимостями при вложенных структурах (`/html`).

**Решение:**
- Плоская структура репозитория: `docker-compose.yml`, `.env` и код приложения в корне.
- `.dockerignore` исключает `vendor/` из контекста сборки.
- **Почему так:** Упрощает онбординг, устраняет конфликты путей и делает поведение локального окружения идентичным продакшену.

## 🚀 Что можно улучшить для Продакшена

Если бы проект масштабировался, следующие шаги были бы приоритетными:

### 1. Производительность
- **Rate Limiting:** Добавить ограничение частоты запросов к внешним API (Telegram/Email), чтобы избежать банов при массовых рассылках.
- **Кеширование конфигов:** В `ChannelDispatcher` добавить кеширование реестра каналов в Redis, если их количество превысит 10-20.
- **Batch Processing:** Для массовых уведомлений реализовать пакетную обработку (отправка 100 уведомлений в одном запросе к API, где это возможно).

### 2. Безопасность и Развитие
- **DTO вместо Модели:** Если каналы начнут требовать данные из внешних источников (например, настройки пользователя из другого сервиса), заменить передачу `Notification` на `NotificationContext` DTO. Это ограничит доступ каналов только к нужным полям.
- **Шифрование чувствительных данных:** Если в сообщениях могут быть персональные данные, добавить шифрование атрибута `message` в модели.

## 🧪 Тестирование

Проект покрыт тестами, которые запускаются в изолированном окружении:

```bash
# Запустить все тесты
make test

# Запустить только юнит-тесты внутри контейнера `make php`
php artisan test --testsuite=Unit

# Запустить конкретный тест внутри контейнера `make php`
php artisan test --filter=NotificationApiTest
```

**Особенности тестов:**
- **Изоляция БД:** Используется SQLite in-memory (`:memory:`) через настройки `phpunit.xml`. Боевая база не затрагивается.
- **Моки внешних зависимостей:** Каналы и диспетчер мокаются через Mockery, чтобы тесты работали быстро и без реальных вызовов к Telegram/Email API.
- **Статический анализ:** `make analyse` (PHPStan level 5) гарантирует отсутствие ошибок типизации.

## 🔧 Конфигурация окружения

Проект использует **единый источник правды** для переменных окружения — файл `.env` в корне.

- **Локально:** Создайте `.env` на основе `.env.example`.
- **Docker:** Переменные автоматически подхватываются из `.env`.
- **Тесты:** Используют настройки из `phpunit.xml` (БД `:memory:`, кеш `array`, очередь `sync`), переопределяя основной `.env`.

> ⚠️ **Никогда не коммитьте файл `.env` с реальными секретами.**
